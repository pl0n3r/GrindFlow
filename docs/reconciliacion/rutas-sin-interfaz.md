## Reconciliación y acciones canónicas

**Resultado exacto:** **7 `CON_INTERFAZ`, 12 `BACKEND_PREPARADO`, 0 `HUERFANA`** en estas 19 candidatas. Ninguna carece de contrato justificante; **no se crea una hoja nueva ni se propone retirar APIs de Library, DSR o staging solo porque no las invoque una pantalla actual**. La ausencia de referencias literales en React/Twig no prueba código muerto, como muestran los siete casos enlazados desde Twig.

**Dos diferencias esenciales entre código preparado y funcionalidad lista:**

1. **Reporte cross-module no registrado.** [`CROSS-MODULE-REPORTS.md`](../CROSS-MODULE-REPORTS.md) admite expresamente que `Http/Reports/CrossModuleReportController.php` queda fuera de la importación de [`routes.yaml`](../../symfony/config/routes.yaml). El código y los tests de [#679](https://github.com/pl0n3r/GrindFlow/issues/679) preparan un reporte privado; **no acreditan un HTTP GET enrutable**. El alcance futuro se gestiona mediante el roadmap existente [#348](https://github.com/pl0n3r/GrindFlow/issues/348); para publicar el endpoint hace falta un leaf con claims sobre el enrutador y una prueba HTTP a través del Kernel, no solo invocar `__invoke()` directamente. El incidente [#903](https://github.com/pl0n3r/GrindFlow/issues/903) ya registra 404 reales en S4 para esa URI y otras; **no duplicar el incidente ni atribuirlo sin evidencia únicamente a caché de Composer**. Que la ruta no esté importada en el código auditado es un hecho separado de la causa real del host.
2. **DSR solo test y B2 sin proveedor operativo.** [#814](https://github.com/pl0n3r/GrindFlow/issues/814) deja las tres API de derechos de datos solo en `APP_ENV=test` y la ruta de borrado solo **registra una solicitud pendiente**. La página pública de privacidad es una **pantalla informativa**, no un cliente DSR; una futura experiencia de titular requiere revisión jurídica y canal autorizado. Direct upload está preparado detrás de un contrato fail-closed y la falta de almacenamiento productivo sigue en [#146](https://github.com/pl0n3r/GrindFlow/issues/146). No configurar proveedor, cambiar fase, fingir 200 de producción ni tratar `202 pending` como borrado.

**Estado de hojas existentes verificado:** [#414](https://github.com/pl0n3r/GrindFlow/issues/414) (colecciones/variantes), [#417](https://github.com/pl0n3r/GrindFlow/issues/417) (permisos), [#679](https://github.com/pl0n3r/GrindFlow/issues/679) (reporte offline), [#799](https://github.com/pl0n3r/GrindFlow/issues/799) y [#814](https://github.com/pl0n3r/GrindFlow/issues/814) (DSR) están **cerradas**; [#348](https://github.com/pl0n3r/GrindFlow/issues/348) (experiencia cross-module), [#146](https://github.com/pl0n3r/GrindFlow/issues/146) (B2) y [#903](https://github.com/pl0n3r/GrindFlow/issues/903) (404 reales en S4) siguen **abiertas**. Una hoja cerrada demuestra entrega de código, no prueba que un endpoint sea público o que los gates de live estén satisfechos.

## Alcance de aceptación de #906

- **AC-01 (matriz):** hay exactamente 19 filas independientes con verbo HTTP, ruta, uso `formulario/enlace/API futura/ninguno`, enlace a código existente, requisito o prueba, veredicto entre los tres permitidos y límite. No se trata un falso negativo del buscador literal como ausencia de interfaz.
- **AC-02 (huérfanas):** cero rutas sin propósito contractual. **No se crea un issue especulativo bajo Factory #1289.** Las carencias de activación y de UI de funciones preparadas permanecen trazadas a hojas/épicas existentes; la eventual publicación exige su propia autorización, tests y V3.
- **AC-03 (`validate`):** se verifica **en el HEAD definitivo del PR de #906**, no en el SHA de referencia ni porque otros PRs hayan pasado.
- **Reversión:** revertir exclusivamente el squash documental. Sin cambios en PHP, Twig, React, tests, `datos.yml`, producción, credenciales, permisos, migraciones ni releases.
